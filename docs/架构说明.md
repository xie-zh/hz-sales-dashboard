# 架构说明：这套系统是怎么运转起来的

> 面向面试讲解，也面向接手维护。讲清「为什么这么做」，而不只是「做了什么」。

---

## 一、整体形态

一句话概括：**把 Excel 当作计算引擎，把 Python 当作搬运工，把静态 HTML 当作交付物。**

```
┌─────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  企业 BI    │──►│  Excel 源表  │──►│  Python 解析 │──►│  静态看板    │
│  (报表服务) │   │ (公式+透视表)│   │  + 口径计算  │   │ (HTML+JSON)  │
└─────────────┘   └──────────────┘   └──────────────┘   └──────┬───────┘
                                                                 │
                                              ┌──────────────────┴──────────────────┐
                                              ▼                                     ▼
                                     ┌────────────────┐                    ┌────────────────┐
                                     │  静态托管/CDN  │                    │  企业微信群    │
                                     │  (看板在线访问)│                    │  (图片+文案)   │
                                     └────────────────┘                    └────────────────┘
```

选择这套形态的原因很实际：业务方的考核逻辑本来就长在 Excel 里（几千个公式、多张透视表、跨表引用），
重写成代码等于把全部口径重新实现一遍，风险极高且无法验证一致性。
**保留 Excel 作为计算引擎，只把「取数 → 搬运 → 呈现」自动化**，是风险最低、见效最快的路径。

## 二、四阶段流水线

主调度器 `ops/bi_refresh.py`，单次执行四个阶段。

### 阶段 1：BI 取数（~19s）

- 并发下载 12 张报表（Playwright 复用登录态，避免反复登录触发风控）
- 每张报表落盘后校验文件完整性（大小 / 首行表头 / 修改时间）
- 失败重试有限次，超时即记入 `partial` 列表，不阻塞后续阶段

**设计要点**：取数失败不阻断构建。用上一版数据继续跑，并在页面顶部显示「数据未更新」横幅——
比整站构建失败、页面打不开要好得多。

### 阶段 2：Excel 写入（~14s）

这是整个链路最脆弱的一环，原因在于 **openpyxl 会丢失公式缓存值**。

Excel 文件里的公式单元格存了两份东西：公式本身（`=XLOOKUP(...)`）和上次计算的缓存值（`42`）。
openpyxl 读写只保留公式、丢掉缓存，于是下游用 `data_only=True` 读出来全是 `None`。

源表有 **2.8 万个公式**、9 张透视表，其中约 700 个 XLOOKUP 跨表引用，不可能重写。

**方案**：走 WPS COM 自动化。

```python
app = win32com.client.Dispatch("Ket.Application")   # WPS 表格
wb = app.Workbooks.Open(path)
ws.Range("A2").Resize(n, m).Value = data           # 整块写入，比逐格快两个数量级
app.Calculate()                                     # 触发全表重算
wb.Save(); wb.Close(); app.Quit()
```

**坑在中途**：进程退出后文件句柄未必立刻释放，紧接着读取会拿到旧内容。
所以在写入后加了「等待文件可独占打开」的轮询，成功再进阶段 3。

### 阶段 3：解析与构建（~57s）

三个解析器分别负责三条业务线，互不耦合：

| 解析器 | 职责 | 难点 |
|---|---|---|
| `dashboard_server.py` | 活动量：多 sheet 协同 | 主表不含全部事业部，需挂载额外数据通道 |
| `sanli_parser.py` | 三力：人力四层分级 | 分级门槛随政策变动，门槛值必须配置化 |
| `ry_parser.py` | 网销漏斗逐人拆解 | 漏斗各级字段分散在不同 sheet 的异构结构中 |

构建产物是**自包含的单文件 HTML**：CSS 内联、数据内嵌一段 `<script type="application/json">`、
同时外挂一份 `.json`。页面优先 `fetch` 外挂 JSON（便于增量更新），失败则回退到内嵌数据。

> 这一条是可用性的底线：**看板可以老，但不能白屏。**

### 阶段 4：判变与发布（~7s）

```
build_hash = SHA256(排序后的所有产物内容)
若 build_hash == _published.json 里的 last_hash  →  exit(0)  SKIP
否则上传 → 核验线上可访问 → 写回 hash        →  exit(23) DEPLOY
```

用**退出码**而不是日志文本传递决策结果，调度器侧只需判断 `$?`，无需解析输出。这是长期运维得出的结论：
日志格式会变，退出码契约不会。

## 三、双口径考核：为什么必须分开算

业务上有两套考核，长得很像，但语义完全不同：

| 口径 | 定义 | 分母 |
|---|---|---|
| **当日达标** | 当天活动量是否达到日目标 | 当天在岗且被考核的人 |
| **滚动周合格** | 近 7 天累计活动量是否达到周门槛 | **仅正常考核人员** |

第二套的分母里必须剔除非考核人员（会计 16 人中有 5 人不考核活动量）。
最初把两套合在一起算，周合格率**虚高约 40%**——因为分母多算了不该算的人。

**现在的做法**：两套口径在数据结构上就分开（`total` / `legal` / `kj_activity` 各自独立），
前端 Tab 显式标注口径名称，任何指标卡片的计算都不跨口径引用字段。

## 四、通话质检：ASR + 结构化评分

这是系统里唯一用到 AI 的部分。

### 流程

```
录音文件列表 → 时长过滤（≥10s）→ 增量判断（已转写则跳过）
    → 腾讯云 ASR 长音频转写 → 带时间戳的分段文本
    → LLM 按五维评分（开场介绍 / 痛点价值 / 需求挖掘 / 异议处理 / 加微埋点）
    → 输出结构化 JSON（分数 + 亮点 + 短板 + 改进建议 + 一票否决项）
    → 汇总进看板
```

### 三个关键设计

**1. 增量处理，绝不重复转写**

ASR 按音频时长计费。827 条录音全量重跑一次成本可观。
所以转写结果按录音 ID 落盘缓存，已转写的直接跳过——**这是成本控制的核心**。

**2. 评分维度固定，避免 LLM 自由发挥**

不让模型自由描述「这通电话打得怎么样」，而是给定五个维度 + 1~5 分刻度 + 必须引用原文证据。
输出的 JSON schema 固定，前端才能做聚合、排序、横向对比。

**3. 一票否决（veto）单列**

某些硬伤（如全程未引导加微、虚假承诺）直接判定不合格，不参与加权平均。
这条规则来自业务方——纯看平均分会把「总体不错但踩了红线」的通话评成良好。

## 五、脱敏：为什么不能只替换表层

公开演示版必须脱敏，但难点在于**数据藏在很多意想不到的地方**：

- HTML 里的内嵌 JSON 兜底块
- JS 模板字符串里的变量插值
- 深层嵌套数组（网销漏斗三层结构）
- 字典的**键**本身就是人名（`{"张三": {...}}`）
- 图表配置里的图例文本

只按字段名做白名单处理，必然漏。

**最终方案是双层机制**：

1. **结构化层**：按已知键名（`姓名` / `person` / `工号` / `部门`）对 JSON 做映射
2. **文本层**：从真实数据里**全量提取姓名集合**，对所有文本做全局替换（长姓名优先，避免「张三」先替换掉导致「张三丰」残留）

姓名映射用**确定性哈希**——同一真实姓名永远映射到同一虚构姓名，这样跨页面的关联关系不会断，
但无法反推真人。

> 反面教训：一开始用正则直接删字段，结果前端读 `undefined` 抛错，整页空白。
> 结论写进了规范——**敏感字段置空而非删除，保持数据结构契约稳定。**

## 六、可用性设计

| 场景 | 兜底方式 |
|---|---|
| 外挂 JSON 加载失败 | 回退到页面内嵌数据 |
| 某张报表取数失败 | 用上一版数据 + 顶部横幅提示 |
| 数据无变化 | 指纹判变直接跳过，不重新构建 |
| 页面停留 | 定时自动刷新，但保留当前筛选与滚动位置 |
| 分享转发 | 单文件 HTML，双击即可打开，无需服务器 |

## 七、迁移性

系统从设计起就假设「会换机器、会换账号」，所以：

- **路径零写死** —— 统一 resolver，靠标记文件向上查找项目根
- **配置集中** —— 一个 JSON 描述发布通道、链接、账号、路径
- **环境自检** —— 13 项体检 + 一键修复（建 venv、装依赖、写配置）
- **离线依赖** —— 依赖包随包携带，断网也能建环境

实际验证：换到新机器，从零到跑通全链路，约 15 分钟。
