## 二、简历"项目经历"标准写法（推荐直接复制）

### 项目一：销售运营数据中台 SalesPulse

**角色**：独立负责（需求梳理 → 数据口径设计 → 全链路开发 → 运维）
**周期**：2026.05 – 2026.10　　**技术栈**：Python 3.11 / openpyxl / WPS COM / ECharts 5 / 原生 JS / Windows 计划任务 / 腾讯云 ASR

**背景**
销售团队的考核数据散落在多个 Excel 表里，每天需人工汇总、算达标率、做报表、发群，单份全量报表耗时 40 分钟以上，
且存在口径不一致、跨表引用易错、无历史留存三个硬伤。

**做了什么**

- 设计并实现**四阶段数据流水线**（BI 取数 → Excel 公式重算 → 解析计算 → 指纹判变发布），
  单次全量执行约 100 秒；无数据变化时 20 秒内判定跳过，不产生任何构建与发布开销。
- 交付 **9 个在线看板页面**（活动量 / 三力 / 经营健康度 / 通话质检 / 网销 / 电邀 / 会计 / 业绩 / 订单明细），
  全部为自包含单文件 HTML，零运行时依赖，可离线归档、可任意转发。
- 建立**双口径考核模型**：把「当日达标」与「滚动周合格」在数据结构层彻底分离，
  修正了周合格率因分母混算而虚高约 40% 的历史问题。
- 打通**通话质检链路**：827 条录音增量转写（已转写自动跳过，避免重复计费），
  LLM 按五维固定量表评分并输出结构化 JSON，支持全员横向对比与改进建议。
- 建立**指纹判变发布机制**：产物内容 SHA256 比对，配合退出码语义（`23 = DEPLOY` / `0 = SKIP`），
  调度侧无需解析日志即可决策，杜绝重复上传与无效算力消耗。

**难点与解决**（面试重点）

| 难点 | 突破方式 |
|---|---|
| 源表 2.8 万个公式 + 9 张透视表，openpyxl 读写丢失公式缓存值，下游全读到 `None` | 改用 WPS COM 整块写入并触发重算，写入后轮询等待文件句柄释放再进下一阶段 |
| 手动运行成功、计划任务必定失败 | 定位到高完整性进程不读 `HKCU` 用户级 COM 注册；验证降权、`CreateProcessAsUser`、经 explorer 启动三条路均无效后，改为启动时把 ProgID/CLSID 自愈写入 `HKLM` |
| 某事业部人员在看板上"消失" | 排查确认是源表结构如此（主表 sheet 不含该事业部），为其单独挂载数据通道，前端按数据存在性自动显隐 |
| 页面偶发整页空白 | 定位为数据字段被裁剪后前端读 `undefined` 抛错中断渲染，确立"敏感字段置空而非删除，保持数据结构契约"的规范，并加内嵌数据兜底 |

**结果**
- 报表产出从人工 40 分钟/次 → 全自动，日更 9 个页面
- 数据口径统一，跨部门对数争议归零
- 系统迁移到新机器从零到跑通全链路约 15 分钟（路径零写死 + 13 项环境自检 + 一键修复）

### 项目二：BI 报表自动化流水线 ReportFlow

**角色**：独立开发　　**技术栈**：Python / Selenium / pywin32 COM / TOML / Tkinter

**背景**
每天需从 BI 系统手工下载 10 余张报表，再按固定规则跨表复制 Sheet、导出 HTML、投放至 Web 目录，
重复劳动且极易漏步。

**做了什么**

- 实现「下载 → 跨表复制 → HTML 转换 → 后处理 → 发布」五段式管道，支持一对一/一对多/多对多 Sheet 映射。
- 开发**可视化配置编辑器**（Tkinter）：动态表单、Treeview 导航、copies 关系批量粘贴、配置校验、自动备份，
  让非技术同事也能自行调整取数规则，不必改代码。
- 实现 COM 引擎进程管理与超时回收，解决 Excel/WPS 进程残留导致的文件占用问题。
- 加入磁盘空间监控与自动清理策略，长时间无人值守运行不因磁盘写满而中断。

**结果**：每日手工操作从约 30 分钟压缩为一次双击，取数规则变更由业务方自助完成。

### 项目三：企微数据战报机器人 BriefKit

**角色**：独立开发　　**技术栈**：Python / Playwright / 企业微信 Webhook / 定时任务

**背景**
看板虽已上线，但一线管理者习惯在群里看结论，不愿主动打开系统。

**做了什么**

- 将看板数据渲染为**图片 + Markdown 文案**，按三个时点定点推送至企业微信群，三条独立链路（活动量 / 三力 / PK）。
- 设计**灰度发送**：先发测试群验证渲染与文案，确认后再发正式群。
- 处理企业微信 aibot 的能力边界：markdown 无 `mentioned_list` 字段，`<@userid>` 会被原样渲染成乱码，
  统一改为纯文本 `@姓名` 方案。
- 确立**失败只报错不重试**原则：发送失败仅回传 errcode/errmsg，避免重复刷屏造成事故。

**结果**：战报触达率显著提升，管理者无需登录系统即可掌握当日达标情况。

## 四、面试可能被追问的 8 个问题（附答案要点）

**1. 为什么不用 React / Vue？**
数据规模百人级、页面 9 个，且核心诉求是"单文件可独立运行、可离线归档、可任意转发"。
纯静态 HTML 天然满足，引入构建链只会增加部署复杂度。技术选型服从交付形态，不是越新越好。

**2. 数据从哪来？为什么不直接连数据库？**
业务方的考核逻辑本来就长在 Excel 里——几千个公式、多张透视表、大量跨表引用。
重写成代码等于把全部口径重新实现一遍，风险高且无法验证一致性。
保留 Excel 作为计算引擎、只自动化"取数→搬运→呈现"，是风险最低的路径。

**3. 怎么保证数据不重复发布、不浪费资源？**
产物内容做 SHA256 规范化哈希，与上次发布指纹比对，一致则整段跳过。
用退出码（23 / 0）传递决策，而不是让调度器去正则匹配日志——日志格式会变，退出码契约不会。

**4. 双口径为什么必须分开算？**
「当日达标」看当天在岗的考核人数，「滚动周合格」的分母只能算正常考核人员。
会计 16 人里有 5 人不考核活动量，混在一起算会让周合格率虚高约 40%。
所以两套口径在数据结构层就分开，前端显式标注，任何指标卡片不跨口径引用字段。

**5. ASR 成本怎么控？**
按录音 ID 做转写结果缓存，已转写的直接跳过。827 条录音只在首轮全量跑一次，之后都是增量。
音频按秒计费，这一步不做，成本会失控。

**6. LLM 评分怎么保证可比性？**
不让模型自由描述，而是给定五个固定维度 + 1~5 分刻度 + 必须引用原文证据，输出 JSON schema 固定。
另设"一票否决"单列——某些硬伤（全程未引导加微、虚假承诺）直接判不合格，不参与加权平均，
否则"总体不错但踩了红线"的通话会被评成良好。

**7. 脱敏为什么不能只替换姓名？**
数据藏在很多意想不到的地方：HTML 内嵌 JSON 兜底块、JS 模板字符串插值、深层嵌套数组、
字典的键本身就是人名、图表图例文本。
所以做双层：结构化字段映射 + 从真实数据全量提取姓名集合做全局文本替换（长姓名优先，避免"张三"先替换掉"张三丰"）。

**8. 这个项目你最大的收获是什么？**
技术上最大的一条是"契约稳定性比字段整洁重要"——脱敏时直接删字段，前端读 undefined 就白屏；
改成置空后一切正常。业务上最大的一条是"口径要写进数据结构，不能只写在文档里"，
否则不同人算同一个指标还是有三个答案。
